# 온라인 TEAM 리콜 신청 Excel: Phase 1

## 범위와 근거

현재 받은 자료는 Excel 파일이 아니라 11개 컬럼과 예시 값을 설명한 요청 텍스트다. 따라서 아래는 **설명에 맞춘 신청/발주 데이터 파서 규칙**이다. 실제 파일의 시트 이름, 헤더 위치, 셀 형식, 메모 문구 분포와 값 빈도는 아직 확인하지 못했다. 이 형식으로 약 15,000건의 리콜 대상 원본 데이터를 확정하지 않는다. 판매 채널과 주문번호는 이 형식에 없으며 생성하지 않는다.

후속 설명으로 시트명 `자산업로드양식`, 사용 범위 `A1:K8`, 고객 데이터 1행, 주소지 열의 안내 1행, 하단 안내 3행, 빈 행이 확인되었다. 실제 `.xlsx` 파일은 아직 전달되지 않았으므로 이 배치를 테스트 워크북으로 재현해 검증했다. 재현 결과: 데이터 1행(`review`, 시리얼번호 누락만 해당), 안내 4행, 빈 행 2행. 실제 파일 직접 검증은 별도로 남아 있다.

기존 Python 모델과 서비스는 `snake_case` 필드명을 사용하므로 파서의 내부 필드에도 같은 규칙을 적용했다. DB 모델이나 컬럼은 이번 Phase에서 만들지 않았다.

## 행 분류와 검증

`preview_recall_applications`는 각 행의 1부터 시작하는 실제 시트 행 번호, 원본 컬럼별 값(`raw_data`), 내부 데이터(`data`), 문제 목록(`issues`)을 돌려준다. 최대 앞 30행에서 11개 헤더를 찾고, 현재 신청 데이터 형식에 맞지 않는 파일은 거부한다. 전혀 값이 없는 행은 `blank`, 명시된 업무 안내 문구만 있는 행은 `instruction`이며 둘 다 `excluded`다. 안내 문구 판별은 제한된 문구 목록과 데이터 유무에 의존한다. 실제 파일 확인 후 목록을 조정해야 한다. 그 외 값이 일부라도 있는 행은 `data`로 남겨 검증한다. 부족한 값을 이유로 자동 폐기하지 않는다.

상태는 `valid`, `duplicate`, `error`, `review`, `excluded`다. 행에는 복수의 검증 코드가 함께 들어갈 수 있다. 오류가 중복보다 우선 표시되고, 중복이 검토 필요보다 우선 표시된다. 개수 집계의 `total`에는 제외 행을 넣지 않는다.

- `MISSING_REQUIRED`: 고객명, 연락처, 주소 중 빈 값.
- `INVALID_PHONE`: 공백과 하이픈을 제외한 값이 `010` + 숫자 8자리 형태가 아님. 문자나 다른 기호는 지우지 않아 오류로 드러낸다.
- `INVALID_QUANTITY`: 수량에 값은 있으나 양의 정수가 아님. 빈 수량의 필수 여부는 미정이다.
- `INVALID_DATE`: 신청일자 또는 회수 일자의 값이 있지만 날짜 변환 실패. `YYYY.MM.DD`, `YYYY-MM-DD`, `YYYY/MM/DD`, Excel 날짜 셀 및 숫자 날짜를 처리한다. 원본값은 `raw_data`에 남긴다.
- `REVIEW_REQUIRED`: 시리얼번호 누락 또는 매우 짧거나 `미정`·`없음` 같은 주소. 이는 주소의 진위 판정이 아니다.
- `DUPLICATE_SERIAL`, `DUPLICATE_PHONE`: 시리얼번호 우선, 연락처 다음 순서로 표시. 둘 다 발견되면 둘 다 보존한다.

파일 내부 중복은 먼저 나온 행 번호를 `matched_row_number`로 기록한다. 향후 업로드 단계에서 기존 데이터를 `existing_records`에 전달하면 기존 항목의 `id`와 진행 상태(`status`)를 문제별로 기록한다. 진행 중과 처리 완료를 구분할 자료만 준비하며 현재 DB 조회나 덮어쓰기는 없다. 한 연락처에 여러 고객이 있을 수 있으므로 전화번호를 고유키로 간주하지 않는다. 시리얼 중복도 자동 수정 근거로 사용하지 않는다.

`source_filename`, `upload_batch`, `uploaded_by`, `uploaded_at`은 향후 업로드 흐름에서 **명시적으로 전달할 수 있는 메타데이터**다. 현재 단계에서는 업로드가 없어 자동으로 값을 생성하지 않는다. 동의값도 표준 enum으로 임의 변환하지 않는다.

## DB 생성 전 확인할 사항

1. 실제 `.xlsx`의 헤더 행, 시트 구성, 추가 컬럼, 빈 행·설명 행의 실제 패턴.
2. 시리얼번호와 수량·신청일자의 필수 여부, 주소 검토 기준.
3. 휴대폰 외 연락처 허용 여부와 숫자로 저장되어 맨 앞 0이 사라진 셀 처리 방침.
4. 동의값의 실제 종류와 표준 상태, 회수/출고 의미.
5. 같은 시리얼·연락처의 여러 신청 건을 구분하는 업무 규칙 및 진행/완료 상태 명칭.
6. 향후 별도 리콜 대상 Raw Data의 식별자, 판매 채널·주문번호, 신청 데이터와의 매칭 기준.
7. 업로드 배치의 보존 기간, 취소/재등록 방침, 개인정보 접근 범위.

## Phase 2 연결점

리콜 관리의 비활성화된 두 등록 버튼에서 파일 선택과 미리보기를 연결할 수 있다. `접수 데이터 등록`은 이 신청 데이터 파서를 사용하고, `리콜 대상 등록`은 별도 Raw Data 샘플을 받은 뒤 독립 파서를 정의한다. 미리보기에서 행별 문제와 파일 내부/기존 데이터 중복을 확인한 다음, 사용자 확인을 거쳐 최종 등록 정책과 DB/API를 결정한다. 발주·출고·회수·SMS는 이 단계의 연결 대상이 아니다.
