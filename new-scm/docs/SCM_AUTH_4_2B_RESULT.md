# 신규 SCM 4-2B 인증 연동 판정

2026-10-27. 기존 자산관리 소스는 정적 분석만 했다. 기존 DB, 운영 인증 API, NAS에는 접근하지 않았다.

## 판정: C안, 실제 통합 로그인 연동 미완료

기존 `GET /auth/me`는 정상 Bearer JWT의 HS256 서명과 만료를 검사하고 `sub`의 기존 `users` 행을 조회해 `is_active`를 확인한다. 응답의 숫자 `id`는 검증된 기존 계정의 식별자로 쓸 수 있다. 다만 현재 선택 화면에서 **독립 신규 SCM으로 인증값을 전달하는 경로가 없고**, 신규 SCM DB에도 그 `id`를 연결할 고유 매핑 및 권한 데이터가 없다. 기존 JWT 서명키를 공유하거나 브라우저의 이름·ID만 신뢰하지 않고 이 둘을 해결할 수 없다.

| 완료 기준 | 결과와 근거 |
|---|---|
| 1. 인증정보의 안전한 인계 | 미완료. 기존 선택은 `/scm-preview` iframe을 열 뿐이다. |
| 2. 신규 백엔드의 기존 API 검증 | 미완료. 신규 `AuthVerifier`는 `UnconnectedVerifier`이고 모든 Bearer를 거부한다. |
| 3. 고유 사용자 매핑 | 미완료. SCM `users`에 외부 주체 키가 없다. |
| 4. SCM 접근권한 확인 | 설계/공통 검사만 존재. 실제 사용자 grant 저장소가 없다. |
| 5. 별도 로그인 없는 독립 진입 | 미완료. 선택 버튼은 독립 빌드로 연결되지 않는다. |
| 6. 만료·위조·권한 부족 차단 | 미연결 상태의 401/Mock 주체의 403만 확인. 실제 JWT 검증은 미검증. |
| 7. 기존 시스템 변경 없음 | 이번 작업에서 유지. |
| 8. 기존 DB·NAS 변경 없음 | 이번 작업에서 유지. |

## 코드로 확인한 인증·진입 경로

1. `frontend/src/api/client.js`는 토큰을 원본 출처의 `localStorage` 키 `assetManager.accessToken`에 보관하고 요청에 `Authorization: Bearer`를 붙인다. 기존 `frontend/src/main.jsx`는 시작 시 `/auth/me`를 호출하고 401 또는 로그아웃 시 토큰을 지운다.
2. `backend/app/api/routers/auth.py`의 `GET /auth/me`는 `UserRead(id, username, name, role, is_active, menu_permissions)`를 반환한다. `backend/app/core/auth.py`가 JWT 서명·`exp`·사용자 활성 상태를 확인한다. `POST /auth/logout`은 접근 로그를 남기지만 JWT 폐기 처리는 없다. 별도 갱신 API도 확인되지 않았다.
3. `frontend/src/App.jsx`의 시스템 선택은 `scm_app` 진입 여부만 판단해 `ScmSiteLayout`을 렌더한다. `frontend/src/components/scm/ScmSiteLayout.jsx`는 `/scm-preview/index.html` iframe을 열며 현재 `postMessage`는 화면 이동과 작업기록 요청/응답에만 사용한다. 인증값 인계 메시지는 없다.
4. 원본 `frontend/package.json`의 `build:scm-preview`는 원본 `scm-preview-src`를 빌드한다. 독립 `new-scm/frontend` 빌드가 아니다. 원본 SCM 진입권한 `scm_app`은 신규 SCM 메뉴·행위 grant와 동일하지 않다.
5. 로컬 개발 출처는 원본 프론트엔드 `127.0.0.1:5173`, 독립 SCM `127.0.0.1:5174`로 포트가 달라 `localStorage`가 격리된다. 실제 운영 출처와 TLS/내부망 경로는 확인되지 않았다. 동일 출처로 제공하더라도 신규 API의 서버 측 인증 검증은 필요하다.

## A/B안이 현재 성립하지 않는 정확한 지점

- **A안:** 신규 백엔드가 기존 `/auth/me`에 원본 Bearer를 서버 간 전달하면 기존 서버의 서명·만료·활성 확인을 재사용할 수 있다. 그러나 현재 독립 앱/백엔드에 Bearer가 전달되지 않는다. 원본 JWT를 URL로 넘기거나 비밀키를 복사하는 대안은 사용하지 않는다. 인증 서버가 응답하더라도 SCM 사용자 매핑과 grant가 없으면 403으로 닫혀야 한다.
- **B안:** 원본 `/scm-preview`는 별도 정적 앱이다. 원본 라우팅이나 배포를 건드리지 않고 그 iframe에 독립 앱을 싣거나 토큰 인계 코드를 추가할 수 없다. 기존 `postMessage`에는 인증 계약이 없다.
- 현재 신규 프론트엔드는 업무 화면을 렌더하지 않고, 신규 백엔드의 인증 API와 미구현 업무 API는 미연결 상태에서 401이다. C안의 안전한 유지 상태다.

## 실제 연동에 필요한 최소 변경 계약 (이번 단계에서는 실행 금지)

권장 경로는 기존 인증 서버가 현재 로그인·`scm_app` 진입권한을 확인한 뒤 SCM 전용 **짧은 수명의 일회성 교환 코드**를 발급하고, 독립 SCM 백엔드가 고정된 인증 서버와 서버 간 교환하는 것이다. 코드에는 SCM audience, 만료, nonce, 1회 사용을 강제한다. 정확한 허용 origin과 `postMessage`의 `origin`/`source`를 양쪽에서 검사하고 원본 장기 JWT를 URL, 신규 `localStorage`, 로그에 넣지 않는다. 교환 코드는 브라우저 히스토리에 남지 않게 정확한 대상 프레임에 전달한다. 인증 서버 통신은 인증서가 검증되는 HTTPS 또는 검증된 내부 경로, 리디렉션 금지, 짧은 타임아웃, 응답 스키마 검증, 장애 시 401을 요구한다.

**기존 시스템의 최소 소스 후보:** `backend/app/api/routers/auth.py`에 인계/교환 API, `frontend/src/api/client.js`에 인계 요청, `frontend/src/components/scm/ScmSiteLayout.jsx`에 독립 SCM iframe과 정확한 출처의 메시지 전달. 기존 선택 UI를 그대로 두는 경로다. 교환 코드의 1회 사용 상태를 저장할 인증 서버 측 저장소와 배포 라우팅/TLS 설정도 필요하며, 이는 소스 세 파일만으로 충족되지 않는다. 별도 창 이동을 택하면 원본 `frontend/src/App.jsx`의 선택 동작도 변경해야 한다. 이 파일들은 **후속 변경 대상 명세**이며 이번에는 수정하지 않았다. 기존 자산관리 업무 화면과 로그인 흐름은 유지할 수 있지만, 인증 서버에 새 API와 저장소를 추가하는 운영 영향은 별도 검토가 필요하다.

**신규 SCM 내부 후속 작업:** 검증 클라이언트, 교환 코드 수신 경로, 인증 서버 장애/만료 처리, 검증된 주체와 SCM 사용자 연결, 서버 권한 조회, 짧은 SCM 세션의 만료/폐기, 프론트엔드의 인증 확인/401·403 안내 및 허용 메뉴만 표시. 각 업무 API는 메뉴·행위·관리자·행 범위 검사를 별도로 붙여야 한다. `/auth/me` 원본 Bearer 직접 전달 방식은 서버 API를 재사용할 수 있지만, 장기 토큰이 독립 앱에 노출되는 범위와 로그아웃 후 만료 전 재사용을 해결해야 하므로 현재의 최소 안전 계약으로 채택하지 않았다.

## 사용자 매핑·권한 저장소 명세 (DB 변경 없음)

- 기존 검증 ID는 `/auth/me.id`이고, 신규 `users.id`는 별도 PK다. 신규 `users.username`은 고유 인덱스가 있으나 양쪽 시스템에서 동일인이라는 보증이 없다. 이름·이메일·숫자 ID 일치로 자동 연결하지 않는다.
- 신규 SCM에 `(issuer, subject)` 유일 제약과 `scm_user_id`의 `users.id` FK, 매핑 활성 상태, 생성·변경 감사를 가진 연결 저장소가 필요하다. 관리자 승인 또는 신뢰 가능한 프로비저닝으로만 매핑을 등록한다. 매핑이 없거나 중복/비활성일 때 접근을 거부한다.
- `users.status=active`와 별도 `system.access` grant를 모두 요구한다. 메뉴 조회, 등록·수정·삭제, `admin.manage`, `excel.upload`, `bulk.change`, 승인자 분리, 매장/행 범위를 명시적으로 저장한다. `account_type=admin`만으로 관리자 작업을 허용하지 않는다. 기존 `scm_app`은 인계 허용에만 쓰고 신규 업무 grant로 승격하지 않는다.
- `new_scm_ro`는 읽기 전용으로 유지한다. 위 저장소의 생성/프로비저닝과 세션 폐기를 위한 별도 변경 주체·승인 절차가 필요하다. 이번 단계에 DDL, 마이그레이션, 데이터·DB 권한 변경은 없다.

## 기존 시스템을 수정하지 않는 대안과 결정 사항

현재 `/scm-preview`를 기존 미리보기로 유지하고 독립 SCM의 인증 필요 API를 401로 잠가 두는 것이 이번 보호 조건과 양립하는 대안이다. 이 상태는 통합 로그인 완료가 아니다. 사용자는 후속 단계에서 **기존 인증 서버·SCM 진입 코드의 최소 변경 및 SCM 매핑/권한 저장소 구축을 허용할지**, 허용한다면 위 일회성 코드 계약과 운영 출처/TLS/로그아웃 정책을 승인할지 결정해야 한다. 그 전에는 4-3단계의 실제 사용자 업무 API 운영 착수 조건이 충족되지 않는다.

## 4-2B 검증 기록

- `new-scm/backend`의 `python -m unittest discover -s tests -v`: 12개 통과. 미연결 자격정보/임의 ID 헤더 401, 검증기 장애 401, 시스템/메뉴/행위/관리자 grant 부족 403을 Mock 경계에서 확인했다. 실제 서명된 JWT의 위조·만료, 사용자 매핑 실패, 메뉴별 실제 API 호출은 검증하지 않았다.
- `new-scm/frontend`의 `npm run build`: 성공. 현재 소스의 인증 게이트는 `currentUser=null`로 업무 화면을 차단한다.
- 이미 실행 중이던 로컬 `127.0.0.1:5174/`는 HTTP 200으로 응답했다. 이미 실행 중이던 `127.0.0.1:8012/api/v1/auth/me`는 HTTP 404였다. 이는 현재 소스의 미연결 401 동작과 불일치하므로 실행 중 프로세스의 코드 버전/기동 설정 확인 전에는 로컬 서비스의 인증 경계를 검증한 것으로 간주하지 않는다. 서버를 재시작하거나 보호 포트를 변경하지 않았다.
- 실제 브라우저 진입은 미검증이다. 브라우저 자동화 도구가 현재 URL을 충분히 확인하지 못해 안전상 중단됐다. 기존 통합 로그인 계정·JWT·운영 인증 API는 사용하지 않았다.
