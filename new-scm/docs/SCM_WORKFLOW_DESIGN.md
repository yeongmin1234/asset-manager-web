# 업무 데이터 흐름·트랜잭션 설계

2026-10-27 기준. 관계와 허용 **상태값**은 [실측 DB 카탈로그](SCM_DB_CATALOG.md)에서 확인했다. 상태 **전이 순서**는 DB CHECK만으로 알 수 없다. 아래 순서는 4-2 구현 전 검토할 설계안이며, 사용자/운영 규칙 확인 전 확정하지 않는다. 프론트 근거: `CustomerConsulting.jsx`, `AsManagement.jsx`, `SalesManagement.jsx`, `InOutWorkflows.jsx`, `LogisticsManagement.jsx`, `SettingsStage12.jsx`, `contexts/AuthContext.jsx`.

## 상태와 삭제에 관한 공통 원칙

- `CHECK`는 허용 문자열만 보장하며 이전 상태→다음 상태 규칙은 보장하지 않는다. 전이는 서비스 계층에서 행 잠금/현재 상태 검사 후 이력 테이블에 저장한다. `as_requests`, `sales`, `logistics_orders`, `purchase_orders`, `stock_transfers`에는 전용 상태 이력이 있으며, `consultations`와 `goods_receipts`에는 전용 상태 이력 테이블이 없어 `audit_logs`의 활용/신규 이력을 결정해야 한다.
- `is_deleted/deleted_at/deleted_by`가 있는 고객·상담·A/S·판매·물류·발주·입고·직원·공지·메모만 soft delete 대상으로 제안한다. 결제, 재고 원장, 감사 로그, 상태 이력의 물리 삭제는 별도 보존 정책 없이는 API에 넣지 않는다. 복구도 참조/중복/권한 규칙 확인 후 설계한다.
- 결제·입고·출고·재고이동·시리얼 적용은 API 요청이 재시도되어도 한 번만 효과가 나야 한다. `source_type/source_id`나 코드가 FK/유일성을 모두 보장하지 않는 곳에는 비즈니스 멱등 키와 잠금 전략이 필요하다.
