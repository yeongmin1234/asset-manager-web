# 4-2C 통합 로그인 연동 결과 (2026-10-27)

## A. 구현 결과

- 기존 통합 로그인 및 시스템 선택 화면은 유지했다. 시스템 선택의 SCM 버튼은 기존 인증 서버에서 45초짜리 일회성 코드를 받아 신규 SCM 백엔드로 교환한다. 실패 시 화면에 오류를 표시하고 이동하지 않는다. `/scm-preview` 원본은 유지했다.
- 기존 인증 서버는 Bearer JWT와 활성 사용자를 기존 의존성으로 검증한다. `scm_app` 메뉴 권한 또는 기존 관리자 역할만 코드 발급을 허용한다. 코드 원문 대신 SHA-256 해시를 프로세스 메모리에 보관하며 교환 시 원자적으로 제거한다. 서버 간 교환은 별도 32자 이상 비밀키와 고정 `new-scm` audience를 요구한다.
- 신규 SCM은 고정된 기존 인증 서버에 서버 측으로 코드를 교환하고, 반환된 `issuer + subject`로 명시적 DB 매핑을 조회한다. 매핑·활성 상태·`system.access` grant를 통과한 경우에만 30분 전용 HttpOnly 세션을 발급한다. 각 요청에서 매핑과 권한을 다시 조회한다. 직접 URL은 인증 없이는 401 화면으로 제한된다.
- **실제 통합 로그인 성공은 미완료**: 필요한 SCM 매핑·grant 테이블이 아직 없어 실제 사용자에게 세션을 발급할 수 없다. 아래 스키마를 승인·적용하기 전에는 기본 거부한다.

## C. 인증·권한 및 승인 대기 DB 설계

기존 `/auth/me`와 동일한 `get_current_user` 검증 결과의 숫자 ID만 외부 `subject`로 쓴다. 기존 사용자명·이메일·숫자 ID의 우연한 일치로 SCM 사용자를 자동 연결하지 않는다. 신규 SCM `users.id`는 별도 식별자다.

**아래 SQL은 제안이며 실행하지 않았다.** `new_scm_dev`에만 적용할 대상이다.

```sql
CREATE TABLE scm_identity_mappings (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    issuer varchar(80) NOT NULL,
    subject varchar(80) NOT NULL,
    user_id bigint NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    is_active boolean NOT NULL DEFAULT false,
    approved_by bigint REFERENCES users(id) ON DELETE RESTRICT,
    approved_at timestamptz,
    created_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_scm_identity UNIQUE (issuer, subject),
    CONSTRAINT uq_scm_mapped_user UNIQUE (user_id),
    CONSTRAINT ck_scm_mapping_approval CHECK (NOT is_active OR (approved_by IS NOT NULL AND approved_at IS NOT NULL))
);
CREATE TABLE scm_user_grants (
    user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    grant_type varchar(10) NOT NULL CHECK (grant_type IN ('menu', 'action')),
    grant_name varchar(120) NOT NULL,
    approved_by bigint NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    approved_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, grant_type, grant_name)
);
```

관리자 또는 별도 승인 권한을 가진 담당자만 매핑·grant를 생성/변경해야 한다. `new_scm_ro`에는 두 테이블 SELECT만 부여한다. 승인 전에 기존 ID의 실소유자를 별도 확인하고 `is_active=false`로 초안 작성 후 이중 검토하여 활성화한다. grant 기본값은 없음이다. 관리자 기능은 `users.account_type=admin`과 `admin.manage`를 모두 요구한다. 기존 `users` 행은 변경하지 않는다. 적용 시 두 테이블 추가와 읽기 권한 부여 외 기존 데이터 영향은 없다. 실제 마이그레이션·계정 권한 변경은 사용자 별도 승인 대기다.

- 기존·신규 프론트엔드 `npm run build` 성공. 기존 백엔드 `compileall` 성공. 기존 로그인 실제 성공/실패, 자산관리 API, 브라우저 실제 클릭, DB 연결, 운영 세션은 **미검증**이다.

## E. DB·운영 영향과 남은 작업

- 자산관리 DB 변경 없음. 신규 SCM DB 변경 없음. 신규 계정·권한 변경 없음.
- 보호 포트 80·8080·3010·8010 설정 변경 없음. NAS 배포/프로세스 중지/재시작 없음. 로컬 서비스도 재시작하지 않았다.
- 개발 기본값: 기존 프론트 `127.0.0.1:5173`, 기존 백엔드 `127.0.0.1:8010`, 신규 프론트 `127.0.0.1:5174`, 신규 백엔드 `127.0.0.1:8012`. 확인 시점에 5174·8012는 이미 점유 중이었다. 프로세스의 코드 버전은 확인하지 않았고 중지·재시작하지 않았다. 브라우저 통합 동작은 미검증이다.
- 기존 백엔드의 `SCM_HANDOFF_KEY`와 신규 백엔드의 `SCM_HANDOFF_KEY`에 동일한 별도 32자 이상 비밀값을 안전하게 설정해야 한다. 기존 JWT 비밀키와 별개다. `SCM_IDENTITY_BASE_URL`, `SCM_HANDOFF_ORIGIN`, `SCM_FRONTEND_ORIGIN`, 기존 프론트 빌드의 `VITE_SCM_API_URL`, `VITE_SCM_FRONTEND_URL`을 환경에 맞게 설정한다. 서버 간 HTTP는 루프백만 허용하며 그 외는 인증서 검증 HTTPS가 필수다. 브라우저 세션 쿠키가 통과하도록 신규 프론트와 API는 같은 사이트의 HTTPS 호스트로 배치해야 한다.
- 인계 코드와 SCM 세션은 각 프로세스 메모리에만 존재한다. 다중 워커/서버, 재시작, 수평 확장 운영 전에는 원자적 TTL 저장소를 설계해야 한다. 현재 구조의 다중 프로세스 운영은 미지원이다.
- 기존 로그아웃은 기존 JWT의 서버 측 즉시 폐기를 제공하지 않으며 SCM 세션도 자동 폐기하지 않는다. SCM 자체 로그아웃 API는 세션을 폐기한다. **통합 로그아웃은 미완료**다. 운영 전 로그아웃 동기화와 세션 폐기 정책을 확정해야 한다.
- DB 스키마 승인·매핑 생성, 로컬 실제 계정 종단간 검증, HTTPS·쿠키·CORS·CSRF 검증, 다중 프로세스 저장소, 통합 로그아웃이 완료되기 전에는 운영 완료로 간주할 수 없다. 4-3 업무 개발은 인증 기본 거부 상태로 진행할 수 있으나 실제 사용자 접근을 전제로 한 기능 검증은 보류해야 한다.
