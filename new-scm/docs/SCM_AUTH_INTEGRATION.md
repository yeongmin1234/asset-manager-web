# 신규 SCM 통합 로그인 연동 상태와 후속 계약

## 현재 상태

**C안, 안전한 연동 경로 미완성.** 기존 `GET /auth/me`는 JWT 서명·만료와 활성 사용자를 확인하므로 A안의 서버 측 검증에 활용 가능하다. 그러나 원본 시스템 선택은 독립 신규 SCM으로 이동하거나 인증값을 인계하지 않으며, 신규 SCM에는 기존 사용자 고유 ID의 매핑과 SCM grant 저장소가 없다. 신규 SCM은 기존 비밀키를 복사하지 않고, 기존 자산관리 DB나 NAS에 접속하지 않는다. 인증정보 교환/실제 사용자 식별/로그아웃 연동은 구현하지 않았다. `AuthVerifier` 기본값은 모든 자격정보를 거부한다.

## 후속 연동에 필요한 계약 (제안, 미구현)

1. 기존 인증 서버가 로그인 상태와 기존 `scm_app` 진입권한을 검증한 뒤, 독립 SCM 전용 audience와 1회 사용·짧은 만료·nonce를 가진 교환 코드를 발급한다. 기존 로그인 화면은 유지하고 시스템 선택 동작과 인증 서버의 인계 API만 최소 변경한다. 코드는 정확한 허용 origin에만 전달하며 원본 장기 JWT를 URL 쿼리, 신규 SCM `localStorage` 또는 광범위한 `postMessage` 대상에 넣지 않는다. **이 변경은 이번 기존 시스템 수정 금지 조건에서는 실행할 수 없다.**
2. 신규 SCM 백엔드는 고정된 인증 서버 주소로 TLS 인증서 검증이 되는 HTTPS 또는 검증된 내부 경로를 사용해 코드를 교환한다. 리디렉션을 따르지 않고 짧은 타임아웃을 둔다. 진위·audience·만료·1회 사용 및 응답 형식을 확인하고 실패/재사용/통신 장애에는 401을 반환한다. 교환 코드·JWT·Authorization 값은 로그에 남기지 않는다. 기존 `/auth/me`에 원본 Bearer를 서버에서 전달하는 방안도 있으나 안전한 브라우저 인계와 로그아웃 정책이 선행되어야 한다.
3. 검증된 기존 `/auth/me`의 `id`를 고정된 issuer와 함께 신규 SCM 사용자에 유일하게 연결하고 매핑 활성 상태와 `users.status=active`를 확인한다. 현재 스키마에는 외부 주체 연결 키가 없으므로 `(issuer, subject)` 고유 제약, `users.id` FK, 상태/이력을 가진 테이블과 관리자 승인/신뢰된 프로비저닝 절차가 필요하다. 사용자명·이메일·같은 숫자 ID만으로 자동 연결하지 않는다.
4. SCM 전용 세션은 별도 서명키·저장소·만료/회전/폐기 정책을 사용한다. 기존 자산관리 JWT 비밀키를 공유하지 않는다. 원본 로그아웃/계정 중지와 SCM 세션 무효화의 지연 허용치를 정한다.
5. 서버가 `system.access`, 메뉴, API 행위, 매장 범위 grant를 안전한 저장소에서 조회한다. 기본 grant는 비어 있고 관리자는 `account_type`과 별도 관리자 grant를 모두 요구한다.
6. 각 업무 라우트에 `require_permission(menu=..., action=..., admin=...)` 또는 동등한 강제 정책을 부착하고 직접 API 호출, 행 범위, 개인정보 마스킹, 상태 전이를 검증한다. 현재 업무 라우트는 0개다.
7. 원본 시스템 선택은 현재 같은 출처의 `/scm-preview` iframe을 연다. 이 파일은 독립 `new-scm/frontend` 빌드가 아니다. 독립 SCM으로 이동하는 라우팅/배포 변경은 기존 시스템 보호 조건과 충돌한다. 같은 출처 프록시를 마련하더라도 신규 백엔드의 인증 검증을 유지한다.

## 현재 인터페이스 사용법

`app.core.auth.AuthVerifier.verify(credential)`는 서버가 진위를 검증한 `Principal`만 반환해야 한다. 만료·위조·비활성은 `None`을 반환한다. 현재 `UnconnectedVerifier`가 기본으로 설치되어 있으며 환경변수만으로 인증 우회를 켤 수 없다. `Principal`의 grant는 브라우저 payload에서 받지 말고 SCM의 신뢰 가능한 서버 정책에서 산출한다.

`GET /api/v1/auth/me`는 유효한 Bearer 인증과 `system.access`가 모두 필요하다. 연결 전에는 401이다. 401/403 응답은 내부 검증 오류나 자격정보를 노출하지 않는다. `/health`와 상태 API는 공개이며 DB 진단 API는 기존 키를 요구한다.

## DB 변경 계획 (실행 금지)

- 외부 주체 매핑: issuer/subject의 unique 제약, SCM `users.id` FK, 활성 상태/이력.
- 권한: 역할 정의, 사용자/역할별 메뉴·행위 grant, 매장별 범위, 관리자·승인자 분리, 변경 감사.
- 세션: 만료·회전·폐기/재사용 방지 저장소 또는 동등한 외부 인증 계약.
- 기존 `new_scm_ro`에는 쓰기 권한을 추가하지 않는다. 마이그레이션과 실제 데이터 변경은 별도 승인 후 진행한다.

## 프론트엔드 및 완료 기준

독립 SCM은 서버가 인증한 사용자와 grant를 받기 전까지 업무 컴포넌트를 렌더하지 않아야 한다. 인증 확인 중에는 로딩, 401에는 기존 통합 로그인 재인증 안내, 403에는 SCM 권한 없음 안내를 표시한다. 표시 메뉴는 서버가 반환한 메뉴 grant로 제한하고 각 API는 서버에서 별도로 검사한다. 현재 인증 인계가 없으므로 안내 화면만 표시되며 로그인 중복 화면은 없다.

실제 사용자의 원본 선택 → 독립 SCM 진입은 위 인계 경로와 DB 매핑/권한 구조가 허용되고 구축된 뒤 검증해야 한다. 유효/만료/위조 JWT, 원본·SCM 계정 비활성, 잘못된 매핑, 권한 부족, 관리자 위조, 인증 서버 장애, 로그아웃과 만료를 실제 경로 및 직접 API 호출 양쪽에서 시험해야 한다. 현재 단계의 401/403 테스트는 미연결 경계에 한정된다.
